# GitHub README 标准模板 — Agent 执行规范

本文件集中提供 README 写作流程和执行规范。这是给 Agent 的完整规范，正文只有中文，不另写英文规范，也不做中英对照。本文件是 `project/project-agent-instructions.md`。模板在同目录的 `templates/`。整套 README 材料在 `project`。同仓库另有 `releases` 与 `changelog`，分别约束 GitHub Release 正文和项目整体 CHANGELOG，不要混用版式。本套 README 规范、模板与检查脚本适用于本仓库所有者维护的所有 GitHub 项目，包括个人账号下的项目。每份 README 都在标题前放置 OPC.FISH 项目署名。套用之前先核实目标仓库归属；第三方项目应遵循其自身的 README 与署名规则。

本文件只用于项目 README。同仓库的 `releases` 与 `changelog` 分别约束 GitHub Release 正文和项目整体 CHANGELOG，不要混用版式。

- 局部更新前先运行成稿检查保存基线。交付时用同一命令区分本次新增、已修复与仍存在的旧问题；修复本次引入或影响本次内容的问题。范围外旧问题记入交付说明，已有错误仍须如实报告。
- 局部更新以现有双语文件为起点，核对改动的来源，只修改相关段落，保留其余人工编写的内容；同步另一语言并验证受影响的命令、链接及锚点。
- 检查草稿时使用 `--draft`，允许编辑用 `{{TODO: ...}}`，其余检查仍执行。可发布成稿必须清除全部编辑用 TODO 和模板占位符。
- 章节表里标成大多数项目需要的节，不适用时整节删除或改成一句实话，不要编造，也不要留空标题。
例如仅更新安装参数时，先记录既有失效链接；更新两份 README 后检查参数与运行结果。如果仍只报同一个无关旧链接，在交付说明保留原错误及本次验证结果。

新建时使用下列模板。

- `templates/readme-template.md` → 输出为仓库中的 **`README.md`**（英文主文件）
- `templates/readme-zh-CN-template.md` → 输出为仓库中的 **`README-zh-CN.md`**（中文独立文件）

不要把 `*-template.md` 这个文件名写进仓库，也不要把语言切换链接改成模板文件名。模板内部的中英切换已经指向最终文件：

- `./README.md`
- `./README-zh-CN.md`

复制到仓库后保持这两个相对路径即可。

## 1. 硬性规则

1. **先查仓库真实事实，再写 README。** 阅读现有 README、包与清单文件（如 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`）、许可证文件、CI 配置、`docs/`、`examples/`、Makefile/脚本、以及 `CONTRIBUTING.md` / `SECURITY.md` / `CHANGELOG` 等。同时清点已有的 Logo、截图、GIF、演示链接和可核实的示例输出。事实以当前仓库为准，不以记忆、习惯用法或同类项目的常见做法为准。
2. **禁止编造。** 不得虚构或“合理推测”以下任何一项：
   - 许可证名称、SPDX 标识、版权持有人或年份
   - 功能列表，以及支持的语言、平台、版本
   - 安装、构建、运行、测试、部署命令
   - 项目状态（stable、alpha、archived、maintained 等）
   - 徽章（构建、覆盖率、版本、下载量等）及其图片/跳转 URL
   - Logo、界面截图、终端动图、命令输出、基准数据或演示地址
   - 作者、赞助、致谢、安全联系方式
   - 文档站点、社区（Discord、Slack、论坛）等外部链接
3. **未知就不写。** 查不到或不确定时：删除该可选章节；若位置几乎必需但事实未知，在稿中用 `{{TODO: 缺少什么、为什么不能确定}}` 标记，并在交付说明里汇总未知项。禁止用“可能”“大概”“通常是 `npm install`”填空。没有演示素材时省略展示，或改用已核实的代码/输入输出，不要补造视觉内容。
4. **按项目类型裁剪。** 只启用对该类型用户有用的章节与一种主展示方式。不要为了模板完整或“更好看”而堆砌。README 面向使用者，短、可执行、可验证优先于“看起来全面”。
5. **双语同步事实，不要逐字强制一致。** 英文与中文必须共用同一套事实、命令、版本号、文件路径、共享引用、徽章和演示资源。行文按各自语言习惯书写，不要为了对齐句子而写出别扭译文。章节标题可按语言习惯措辞，但信息集合与视觉层级必须对等：一边出现的事实、命令、链接和首屏元素，另一边也要有（或指向同等位置）。
6. **严禁密钥。** 不得写入真实 API key、token、密码、私钥、证书，或连接字符串中的密钥部分。示例只用明显占位符（如 `YOUR_API_KEY`、`YOUR_API_TOKEN`、`$API_TOKEN`）。若仓库里已经出现疑似密钥，不要复制进 README，并在交付说明中提醒维护者轮换。
7. **主文件是英文，中文是独立文件。** `README.md` 为 GitHub 默认主 README（英文）；`README-zh-CN.md` 为单独的中文文件。两份文件在标题之下必须有相对路径的中英切换，当前语言加粗。署名在标题之前。
8. **示例与命令必须可执行或标明未验证。** 不要写找不到入口的伪命令，也不要改写未经证实的参数。
9. **全文最上方保留 OPC.FISH 署名。** 放在标题之前。使用第 5.5 节规定的浅色 SVG、深色 SVG 和 `https://opc.fish` 链接。这是维护者署名，不是可删的装饰，也不要换成项目自己的 Logo。

别人这样使用本仓库：

- 在本仓库阅读规范，或克隆后按某一次提交固定规范文本。生成稿里的署名图地址故意跟着 `main`：这两张 SVG 更新后，已经写好的 README 会一起换成新图。
- 若某个项目要冻结署名，把浅色和深色两张 SVG 复制进该仓库，在两份 README 中改用 `./assets/` 下的相对路径，并在交付说明里写明。
- 不要把本文件或 `*-template.md` 复制进目标仓库。
- 成稿写完后，在 `project` 目录运行 `python3 scripts/check-readme.py pair <README.md> <README-zh-CN.md> --signature remote`，将两个文件参数替换成成稿路径。默认远程署名用 `--signature remote`。若已将两张 SVG 固定到目标仓库并通过 `./assets/` 引用，改用 `--signature local`。

## 2. 推荐工作流

1. **扫描仓库，列出事实清单**：项目名称、已有描述、项目类型、许可证文件、安装入口、最小可运行示例、测试命令、配置项**名称**、文档入口、已在用的徽章及其 URL、已有 Logo/截图/GIF/演示链接、可核实的命令输出或产物。
2. **判定类型并裁剪**：CLI 工具、库/SDK、Web 或带界面的服务、自动化工具、模板/Skills、纯文档，或混合。按第 4、5 节取舍章节与展示方式。不要默认解开全部 OPTIONAL 块，也不要叠多种装饰。
3. **验证 Quick Start（能跑则跑）**：按准备写入的步骤，在干净环境走通“安装 → 一次成功调用/运行”，纯文档则走通阅读路径并核对入口。失败则不要把该命令写成官方步骤；改为记录实际可用的命令，或采用仓库中的命令但明确标明“未在本环境验证”并写出失败原因。不要把未核实的输出或基准数字写进首屏演示。
4. 用英文模板起草 `README.md`。散文占位符写成英文；命令、路径、URL、版本、许可证名称、徽章与演示资源等与中文稿共用。
5. 基于**同一份事实清单**起草 `README-zh-CN.md`。先同步事实与视觉结构，再组织中文表述，不要把英文逐句硬译后再回头改命令。
6. **对照检查**：链接能解析、两边命令一致、无密钥、无无证据章节、语言切换互指正确、未启用的 OPTIONAL 整块已删、短文档没有硬加 TOC、首屏没有把安装和快速开始挤到过远、徽章不超过 4 枚且均已核实、图片有描述性 alt、中英视觉层级一致且锚点已按各自标题本地化、两份文件最上方的 OPC.FISH 署名图片与链接均未被改写。
7. **交付说明**应包含：写了哪些章节、省略了哪些及原因、选择了哪种主展示、哪些命令已验证、哪些是 `{{TODO}}`、自检脚本的结果。署名块不计入“主展示”。

---

交付说明标明「可发布成稿」或「待核对草稿」。次要未知内容可省略；项目用途或必要操作步骤等关键事实缺失时交付草稿。可发布成稿须清除所有编辑用 `TODO` 和模板占位符。检查草稿时可传 `--draft`，允许编辑用 `TODO`，其余检查仍执行。

## 3. 章节清单

### 必需（大多数项目都要有；缺事实则删或改写，不要编）

| 章节 | 写什么 |
|---|---|
| 语言切换 | 相对链接；当前语言加粗。放在标题之后、一句话说明之前。OPC.FISH 署名在标题之前。 |
| 项目名称 | 与仓库或官方名称一致。仅当仓库已有 Logo 文件时才可在语言切换之后展示，不要编造或生成 Logo。 |
| 一句话说明 | 让用户约 10 秒内知道这是什么、给谁用、有何具体价值。须来自仓库描述或可证实的用途，禁止“强大、优雅、革命性”等空话。 |
| 概述 | 它解决什么问题、适用场景。保持极短，不要把文档站点整页搬进来，也不要用长介绍把快速开始推远。 |
| 要求 / 先决条件 | 仅列出经证实的运行时、工具、版本下限。没有证据就不要写“需 Node 18+”这类句子。 |
| 安装 | 经证实的安装方法。多种包管理器只写仓库确实支持或文档已写明的；额外平台步骤可折进 `<details>`，**默认安装命令必须展开**。纯文档项目见第 4 节。 |
| Quick Start | 从零到一次成功运行的最短路径。命令可复制；能写期望结果就写真实的，未知则省略。本节必须展开，不可放进 `<details>`。 |
| 用法 | 核心用法与最常见工作流。细节链接到完整文档，避免把全部 API 贴进 README。 |
| 许可证 | 有适用的许可证文件时写名称并链接该文件。只有明确声明时写明声明来源，许可证文件链接可省略。无文件与明确声明时省略本节。各子包许可不同时标明可核实的适用范围。 |

要求、安装、用法、许可证在大多数项目中需要，模板里默认保留。不适用则整节删除（纯文档通常删掉要求和安装），或改成一句实话（如“本仓库是文档/规范，克隆或在线阅读即可，无需安装”），不要编造，也不要留空标题。

### 条件章节（无证据必须整块删除，不可无证填写）

| 章节 | 仅在以下情况启用 |
|---|---|
| 徽章 | 每一枚的图片 URL 与跳转 URL 都真实、可核对，且状态确实由该服务提供。默认**不超过 4 个**，只放有信息价值的（如版本、构建状态、许可证）。失效或来源不明的一律不用。多枚徽章写在**同一行**，中间用一个空格隔开，横向排成一排。不要每枚单独成行，否则会上下叠成一列。 |
| 主要入口 | 已有文档、公开演示，或本文件中真实存在的「安装」「快速开始」锚点。只放一个链接。没有就删除。 |
| 首屏演示 / 特色展示 | 已有图片、GIF、公开演示链接，或可核实的命令输出/短代码/输入到产物。按第 5 节只选一种主展示。不要用占位图，不要编造输出或基准数据。 |
| 项目状态 | 仓库或官方文档明确说明了成熟度、维护状态或弃用。 |
| 功能列表 | 每条功能已实现且可证实；写成具体收益，不要口号，也不要把路线图愿望写成功能。放在快速开始之后，避免把第一次运行往下推。 |
| 目录（TOC） | 正文较长时再加（经验：超过一屏，或主要章节明显多于 4 个），放在首屏展示之后。短 README 不要加 TOC。按最终保留的标题重写，不要沿用模板里的示例列表。锚点必须跟本文件的标题走。 |
| 重要提示块 | 仅用于真实的限制、风险或必须注意的事项。使用 GitHub 原生 `NOTE` / `WARNING` 等，不要把普通介绍放进提示块。 |
| 折叠块 (`<details>`) | 仅用于次要的长内容（如额外平台安装、较长输出）。不可折叠核心安装或快速开始。 |
| 配置 | 存在真实的配置文件、CLI 标志或环境变量。只写名称、含义、默认值（若已知），不写密钥。 |
| API / 文档入口 | 已有文档站点、`docs/` 或生成的 API 文档。可作为首屏“重要使用入口”链接，但链接必须真实。 |
| 更多示例 | 有 `examples/` 或额外配方，且 Quick Start 不足以覆盖。 |
| 测试 | 有真实、可引用的测试命令。 |
| 构建与本地开发 | 面向贡献者的开发步骤确实存在。用户向 README 里只放最短必要信息，细节指向贡献文档。 |
| 部署 | 项目是服务/应用，且有经证实的部署方式。 |
| 故障排除 / FAQ | 有真实常见问题。不要编一套假 FAQ。 |
| 安全披露 | 有 `SECURITY.md` 或已公布的报告方式。 |
| 贡献 | 有 `CONTRIBUTING.md` 或明确贡献说明；否则最多链到 Issues，不要编贡献流程。 |
| 路线图 | 已有公开路线图。 |
| 变更日志 | 有 `CHANGELOG` 或稳定的 Releases 习惯。 |
| 致谢 / 引用 | 有需要致谢的上游，或项目要求学术引用。 |
| 社区 / 支持 | 有真实的讨论区、邮件列表或官方支持渠道。 |
| 相关项目 | 维护者已标明的官方相关仓库。 |

### OPTIONAL 块如何处理（避免把“可启用”当成“应留下”）

章节顺序：概述和状态保持很短，然后是环境要求、安装、快速开始。功能放在快速开始之后。配置、文档、示例、部署、故障排除属于使用者路径。测试、开发、安全、贡献、路线图、变更日志、社区、致谢、相关项目属于维护者路径，放在后面。

`NOTE` 和 `WARNING` 是两块独立的 OPTIONAL。只启用确有内容的那一块。

模板里用 HTML 注释包起来、并标为 `OPTIONAL` 的块：

- **启用：** 去掉包围的 `<!--` 与 `-->`，填入已核实的真实内容，并删除模板说明文字。不要把注释外壳留在用户可见的 README 里。
- **不需要或无证据：** **整块删除**（含标题、示例标记和注释本身）。不要给用户留下空标题、`TBD`、未替换的 `{{PLACEHOLDER}}`，或一大段未解开的 OPTIONAL 注释。
- 模板中出现某个块，并不表示默认启用。内部待确认只用 `{{TODO: ...}}`，并在交付说明中列出。

## 4. 按项目类型裁剪

**CLI / 工具**

- 内容突出：安装、一条可复制的成功命令、常用子命令或标志、真实的输入/输出示例；仅在确实有用时写关键错误或退出码。
- 展示优先：代表性命令及其真实输出；仅当仓库已有终端动图时再配 GIF。
- 通常不要放：库的 import 示例、API 参考正文。

**库 / SDK**

- 内容突出：语言与版本兼容性（须有证据）、包管理器安装、最小 import + 可运行片段、指向完整 API 文档的链接。
- 展示优先：一段短小但完整、可运行的代码示例。
- 通常不要放：生产部署、服务健康检查。

**Web 应用 / 带界面的服务**

- 内容突出：先决条件、如何本地运行或部署、必要配置项**名称**、如何确认已经启动（真实的健康检查或 URL）、基本使用路径。
- 展示优先：真实界面截图；已有公开地址时再放在线演示入口。
- 环境变量只列名称与用途；示例值必须是占位符。

**自动化工具**

- 内容突出：如何准备输入、如何执行、产物在哪里、如何确认成功。
- 展示优先：真实的输入、执行方式与最终产物，而不是抽象功能清单。

**模板 / Skills 仓库**

- 内容突出：这些模板或技能做什么、如何选用或调用、一个典型场景。
- 展示优先：分类导航与典型调用示例。不要编造未提供的技能列表或参数。

**GitHub Action**

- 内容突出：`uses:` 行、确实存在的输入和输出、最小工作流片段。
- 展示优先：一段可复制的工作流，而不是 Action 市场文案。
- 通常不要放：与该 Action 无关的应用部署步骤。

**Monorepo**

- 内容突出：新用户应该先打开哪个包，以及那个包自己的安装和一次成功调用。
- 展示优先：包的导航表。其余包用链接给出。
- 通常不要放：把每个包的长教程并列在根 README 里。

**浏览器扩展 / 移动应用**

- 内容突出：支持的平台（须有证据）、如何安装开发版或从真实商店安装、最小使用路径。
- 展示优先：仓库里已有的界面截图，或真实商店页面。
- 通常不要放：没有截图时生成的界面图。

**数据 / 模型仓库**

- 内容突出：数据或模型是什么、许可与使用限制（仅当仓库写明）、如何取出一份样本、样本长什么样。
- 展示优先：一份真实输入和对应输出。
- 通常不要放：未在仓库中出现的指标排行榜。

**纯文档 / 规范 / 内容仓库**

- 内容突出：文档覆盖范围、如何阅读或导航、如何预览/构建（仅当仓库确有该命令）、如何提议修改。
- 展示优先：覆盖范围与阅读导航。不要为了“好看”补软件截图或安装步骤。若克隆或在线打开即可阅读，写明这一点。省略不适用的环境要求和安装；快速开始用展开的文字步骤，如「打开规范 → 选择模板 → 查看成稿」，有确实需要的检查命令时另列。参见[英文成稿](docs/project.md)和[中文成稿](docs/project-zh-CN.md)。

**混合项目**

- 以主用户路径作为第一条 Quick Start 和首屏主展示；其余入口用短小节或链接给出，避免并列多套互不相关的长教程或多种装饰。

## 5. 视觉与表达规范

目标是**简洁的开源项目风格**：统一的是品质，不是每个项目都长得一样。先识别类型与主要用户，再选择一种最能解释用途的展示；不要套同一排徽章、大横幅或动效。

### 5.1 首屏

文件最上方固定放 OPC.FISH 署名，位于标题之前。它不占下面的主展示名额，也不要把它写进目录。

首屏其余内容优先呈现下面这些（有真实素材才放，没有就省略，不要用装饰填空）：

1. 项目名称。
2. 中英文切换（紧接标题，见第 7 节）。可选的已有 Logo 放在切换行之后。
3. 一句简短、具体的价值说明。
4. 少量真实、有效、有信息价值的徽章，**默认不超过 4 个**。多枚写在同一行、用空格隔开，横向排成一排。
5. 一个最重要的真实使用入口（如在线演示、文档、或指向安装/快速开始的锚点）。没有这样的链接就省略。
6. 一份最能说明价值的真实演示（截图、动图、已核实的命令与输出，或一段完整短代码）。

让人一眼理解项目，比一眼看到很多装饰更重要。不要用大幅图片、过长概述、徽章墙或居中大横幅，把「安装」和「快速开始」推得过远。先结果，再步骤。

### 5.2 正文更易读

- 概述保持极短，尽快进入演示与快速开始。
- 功能写成具体收益，且必须属实。例如不要只写“支持批处理”，而应写“一次处理多个文件，无需逐个执行”——前提是确实如此。禁止夸大。
- 段落要短：一段讲一件事。比较信息用表格，操作步骤用编号列表。
- 重要限制或风险才使用 GitHub 原生提示块（`> [!NOTE]`、`> [!WARNING]`）。不要把普通介绍放进提示块，也不要到处加粗。
- `<details>` 只折叠次要的长内容（额外平台安装、较长输出等）。**核心安装与快速开始必须展开，不可折叠。**
- 默认使用 GitHub 原生 Markdown；仅在必要时使用简单 HTML（如已有 Logo 的 `img`、`<details>`）。不滥用 emoji、分隔线、居中排版或大型装饰横幅。
- 不要添加访问计数器、与项目无关的技术栈图标墙，或装饰动画。全文最上方的 OPC.FISH 署名按第 5.5 节保留，不要把它当成这类装饰删掉，也不要把它挪到文末。

### 5.3 图片与主题

- 图片使用描述性 alt 文本，说明图里是什么，不要只写 “screenshot” 或 “logo”。
- 仓库内图片优先使用相对路径，避免依赖不稳定的外部图床。
- 确保在浅色、深色主题和窄屏下仍可读：不要让关键信息只出现在过宽的图或必须横向滚动的表里。
- **仅当仓库已同时具备浅色和深色两套内容图时**，才使用 GitHub 主题碎片 `#gh-light-mode-only` / `#gh-dark-mode-only`。它们跟随用户在 GitHub 上选择的主题。缺一种不要编造或生成另一张。
- 这套碎片只用于内容图。文首署名不使用它们，署名的主题机制见第 5.5 节。

### 5.4 双语视觉一致

中英文保持相同的视觉层级与信息结构：同一套首屏元素、同一组已启用章节、同一组徽章与演示资源。章节标题按语言本地化，目录与文内锚点必须跟**各自文件的标题**走（例如英文 `#quick-start`，中文 `#快速开始`），不要把一种语言的锚点复制到另一份文件。

GitHub 锚点由标题生成：英文转为小写，空格变成连字符，去掉大部分标点；中文标题保留汉字，不要写成拼音。同名标题会加上 `-1`。拿不准时以 GitHub 渲染出的锚点为准。

### 5.5 署名

每份生成的 README 在全文最上方保留一块固定署名，表示项目来自 [opc.fish](https://opc.fish)。它不是项目 Logo、徽章或主展示，也不进入目录。

- 放在标题之前，作为文件的第一块内容。不要把它移到许可证之后或全文末尾。
- 两份语言文件使用同一组图、同一个链接。不要重画、换色、裁切、换图或改链接。alt 可以按语言改写。
- 悬停提示显示 `OPC.FISH Project.`，点击图片打开 `https://opc.fish`。
- 浅色用透明底、墨色字的 `opc-fish-project-signature.svg`。深色用透明底、浅色字的 `opc-fish-project-signature-web-dark.svg`。显示宽度 720。不要另做一版，也不要改这两张图的颜色。
- 交付稿只保留下面这一块，不要把本段说明留在用户可见的 README 里：

```html
<a href="https://opc.fish" title="OPC.FISH Project."><picture><source media="(prefers-color-scheme: dark)" srcset="https://raw.githubusercontent.com/YE4IM/readme/main/project%20readme/assets/opc-fish-project-signature-web-dark.svg"><img src="https://raw.githubusercontent.com/YE4IM/readme/main/project%20readme/assets/opc-fish-project-signature.svg" alt="OPC.FISH Project" width="720"></picture></a>
```

- 若使用仓库内固定署名，仅将上述两处远程 SVG 地址替换为 `./assets/` 下对应文件的相对路径，并用 `--signature local` 验证。
- 中文成稿可以把 alt 写成 `OPC.FISH 项目署名`。
- 署名图地址跟着 `main`。`YE4IM/readme` 现为公开仓库，未登录即可加载。若该地址以后不可公开，仍然保留这块 HTML，并在交付说明中写明图片目前无法在仓库外加载。
- 署名使用 `<picture>` 和 `prefers-color-scheme: dark`，跟随系统配色。这不一定等于用户在 GitHub 上单独选择的浅色或深色主题，所以不要把署名改成 `#gh-light-mode-only` / `#gh-dark-mode-only`。
- 在非 GitHub 的预览里，两张署名图可能同时出现。

## 6. 未知、冲突与验证失败

- **多种安装方法互相矛盾**：以当前默认可验证的文档或脚本为准。其他方法只有在验证后（或仓库明确并列支持时）才写；次要方法可放进 `<details>`，不要因此打乱首屏和快速开始。
- **旧 README 与代码不一致**：以代码、包配置和能跑通的命令为准，并在交付说明中指出差异。
- **许可依据有差异**：按第 3 节核对适用的许可证文件或明确声明，尤其是独立子包的许可范围。
- **徽章状态不确定**：不放该徽章。无法确认仍有效的旧 badge URL 一律省略。即使有多枚有效徽章，默认也只选不超过 4 个最有信息价值的。
- **缺少一句话描述**：只能根据仓库已有描述、文档标题或显而易见且可证实的用途来写。仍不够明确时，用 `{{TODO: 一句话说明待维护者确认}}`，不要撰写营销文案。
- **没有 Logo、截图、动图或演示地址**：省略该展示，或改用已核实的代码/输入输出。不要生成 Logo、不要伪造界面或终端画面、不要编造输出或基准数据。
- **Quick Start 无法验证**（缺环境、私有依赖、需要密钥等）：可以写仓库中已经存在的命令，但必须标明“未在本环境验证”，不要假装已验证，也不要把未核实输出当作首屏演示。

## 7. 语言切换（最终文件名）

两份文件放在同一目录（通常是仓库根目录）。使用相对链接，不要用 GitHub 绝对 URL 做语言切换（fork 与换分支会失效）。

英文 `README.md` 在标题之下：

```markdown
[**English**](./README.md) | [中文](./README-zh-CN.md)
```

中文 `README-zh-CN.md` 在标题之下：

```markdown
[English](./README.md) | [**中文**](./README-zh-CN.md)
```

若 README 不在仓库根目录，相对路径按实际位置调整，但文件名仍必须是 `README.md` 与 `README-zh-CN.md`。

检查器校验常见 Markdown 相对链接、ATX 或 Setext 标题锚点和显式 HTML 锚点。含复杂 Markdown、GitHub 特殊路径或渲染生成的锚点，交付前在目标 GitHub 页面预览核对。

目录锚点按各语言标题生成。英文 `# Quick Start` 对应 `#quick-start`。中文 `# 快速开始` 对应 `#快速开始`，不要写成拼音。GitHub 会把重复标题加上 `-1`。

## 8. 占位符约定

- 模板使用显式 `{{PLACEHOLDER_NAME}}`。交付给用户的 README 中不应残留未替换的占位符。编辑用 `{{TODO: ...}}` 仅可留在待核对草稿。
- **两边必须相同**的值：项目名称、命令、代码片段中的标识符、共享资源路径和 URL、版本号、徽章 URL、许可证名称、环境变量名称、配置键名、演示资源路径、文首署名的两张图片地址、宽度 720 与 `https://opc.fish`。安装和快速开始的代码块语言名也相同，按实际执行环境或编程语言标记，例如 Bash 用 `bash`、PowerShell 用 `powershell`。
- 产物、PR、Issue、校验文件等共享引用指向同一目标；本页锚点、适用的语言切换链接和同主题的官方本地化文档可使用等价地址，例如英文 `#quick-start` 对应中文 `#快速开始`，英文迁移指南可对应同主题的官方中文版。
- **按文件语言分别填写**的值：一句话说明、概述、功能描述、用法说明、注意事项、图片 alt、`<details>` 的摘要、提示块正文等散文。
- 可执行命令、参数和文件名保持原样；代码注释与示例输出可按语言改写。围栏和行内代码里的模板字段也须替换。脚本按块比较常见中英文标题下安装与快速开始的代码围栏语言及 shell 命令，允许本地化注释、独立输出围栏与带提示符示例中的输出；内联命令和其他语言的代码内容由审阅者对照。
- 目录锚点按各语言标题生成，不要共用另一语言的锚点。

## 9. Quick Start 质量

- 按真实顺序写，命令可复制；必要的工作目录、前置条件不要省略。
- 成功长什么样（输出、打开的地址、生成的文件）只写真实已知的；未知就省略“期望结果”。
- 示例代码应可运行，import/包名与仓库一致。
- Quick Start 只覆盖最短成功路径，且必须展开显示；完整教程放到 Usage 或外部文档。
- 不要让首屏装饰、长概述或 TOC 把本节挤到很远。
