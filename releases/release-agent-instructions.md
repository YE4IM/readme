# GitHub Release Notes 标准模板 — Agent 执行规范

本文是给 Agent 的执行规范，**不是**给仓库用户看的 Release 正文。生成或更新 GitHub Release 说明时，先读完本文件，再填写同目录下的：

- `release-template.md` → 输出为 GitHub Release 的**单篇正文**（中英双语同文，英文在前、中文在后）

不要把 `release-template.md` 这个文件名写进 Release 正文。GitHub Release 是单篇内容，不要拆成仓库根目录那种 `README.md` / `README-zh-CN.md` 两份文件。

## Release 标题

GitHub Release 标题默认使用真实发布标识（通常是完整 Tag），保留项目的前缀和预发布后缀，例如 `v2.0.0-rc.1` 与 `v2.0.0`。项目有明确的标题惯例时沿用，并保留预发布身份。功能摘要写在正文开头。

可对照[维护线正式补丁](./examples/patch.md)与[带下载步骤的首次发布](./examples/initial.md)。两份示例使用虚构数据和不可用的示例链接，供格式验收。

结构约定：

- 完整英文在前，使用 `---` 分隔后，再写完整中文。
- **不要**单独注明 “English / 中文” 语言标题，也**不要**添加中英文切换链接或 `#english` / `#中文` 这类页内锚点。两侧内容各自直接使用 `##` 二级标题组织章节（例如 `## Breaking Changes` 对 `## 破坏性变更`），保持结构与视觉层级对等，避免 `#` 标题之后直接跳到 `###`。
- **不要**在正文顶部或内容中单独写版本号标题，也不要重复项目名、发布日期、版本类型或上一版本等元信息。GitHub Release 页面本身已展示标题与 Tag / 版本号。收集事实时仍须先确认本次对应的 Git Tag 与提交范围，以保证改动准确，正文可按证据保留兼容范围、迁移条件、安全影响和真实命令中的版本号。

## 1. 硬性规则

1. **先查真实 Git / Tag / PR / Issue / Release Assets 事实，再写正文。** 阅读当前仓库的标签与发布时间、同一包、同一发布线的上一可比版本与当前 Tag 之间（或等价提交范围）的 commits、已合并 PR、关联 Issue、既有 `CHANGELOG`、发布说明草稿、CI 发布工作流，以及本次 Release 实际挂上的附件与校验和（如有）。同时核对该次发布真实支持的安装或升级方式。事实以仓库与 GitHub 上可核对的记录为准，不以记忆、习惯用法或同类项目的常见做法为准。收集事实时必须确认本次对应的 Git Tag 与提交范围；发布前尚无 Tag 时固定目标提交，区分拟用标识与已存在的 Tag，但不要把版本号写进正文标题或头部。
2. **禁止编造。** 不得虚构或“合理推测”以下任何一项（这些信息用于核对事实；其中版本号、项目名、日期与类型不必写进正文）：
   - 项目名称、版本号、Git Tag、发布日期、版本类型（`Stable`、`Pre-release`、`Hotfix` 等）
   - 变更内容、影响范围，以及性能、体积或其他基准数据
   - PR / Issue 编号、Compare 链接、提交哈希、贡献者 `@handle`
   - 安装、升级、迁移命令，以及最低运行环境变化
   - Release Assets 的文件名、大小、平台、下载链接或 SHA256 等校验和
   - 截图、GIF、终端输出、演示地址或未经验证的命令结果
   - 安全公告编号、CVE、已知问题列表
3. **未知就不写。** 查不到或不确定时：删除该可选章节；若位置几乎必需但事实未知（例如确有破坏性变更，但迁移步骤写不全），在稿中用 `{{TODO: 缺少什么、为什么不能确定}}` 标记，并在交付说明里汇总未知项。禁止用“可能”“大概”“通常是 `npm i package@latest`”填空。没有演示素材时省略展示，或改用已核实的代码/输入输出，不要补造视觉内容。
4. **按版本类型与项目类型裁剪。** 只启用对该次发布、对该类用户有用的章节。不要为了模板完整或“看起来全面”而堆砌空节。Release Notes 面向使用者，短、可执行、可验证优先：写清“解决了什么 / 带来什么变化”，用面向用户的文字概括原始提交。
5. **双语同步事实，英文在前、中文在后，行文各自地道。** 英文与中文必须共用同一套事实、PR/Issue 引用、命令、共享引用、资源文件和校验和。先写完整英文，以 `---` 分隔后再写完整中文。行文按各自语言习惯书写，不要为了对齐句子而写出别扭译文。章节标题可按语言习惯措辞，但信息集合与视觉层级必须对等：一边出现的事实、命令、链接和章节，另一边也要有。不要在任何一侧补写版本号标题或语言标题。
6. **严禁密钥。** 不得写入真实 API key、token、密码、私钥、证书，或连接字符串中的密钥部分。示例只用明显占位符（如 `YOUR_API_KEY`、`$API_TOKEN`）。若提交说明、示例或附件说明里已经出现疑似密钥，不要复制进 Release 正文，并在交付说明中提醒维护者轮换。
7. **正文是单篇双语 Release，不是两份 README。** 交付一篇用于 GitHub Release 描述框的 Markdown，状态见第 2 节。不要输出分文件结构，也不要在正文里链到模板文件名。**不要**单独注明 “English / 中文” 语言标题，也**不要**添加中英文切换链接。**不要**在正文中写版本号标题或重复项目名、发布日期、版本类型、上一版本等元信息：GitHub Release 页面已展示标题与 Tag。
8. **命令、链接与引用必须可执行或可核对，否则标明未验证。** 不要写找不到入口的伪命令，也不要改写未经证实的参数。未验证的安装/升级命令必须在正文中说明，并在交付说明中列出。

## 2. 推荐工作流

1. **收集 Tag 范围与变更事实**：当前 Tag / 版本号、同一包、同一发布线的上一可比版本（若有）、发布日期、版本类型、仓库路径 `owner/repo`、该范围内的 commits / 已合并 PR / 关联 Issue、贡献者、本次 Release Assets、已核实的安装或升级方式、已有截图/GIF/可核实输出。这些元信息用于核对范围与裁剪章节，不要写进正文标题或头部。
2. **判定版本类型与项目类型并裁剪**：首次发布、Major、Minor、Patch/Hotfix、Pre-release；以及 CLI / 工具、库 / SDK、Web 应用 / 服务、桌面或移动应用、自动化工具、模板 / Skills 仓库。按第 4、5 节取舍章节与展示方式。不要默认解开全部 OPTIONAL 块，也不要叠多种装饰。
3. **合并归类，面向用户改写**：将零碎、重复或仅内部的 commits 合并为清晰的用户可见条目。丢弃 `fix typo`、`wip`、`merge branch` 这类对使用者无意义的记录。按破坏性变更、新增、优化、修复、安全、弃用与移除、维护与依赖等归类。
4. **确定启用章节**：只保留有证据且对该版本有用的章节。预发布必须启用警示；有不兼容改动必须启用破坏性变更，并给出可核实的迁移步骤或 `{{TODO}}`。
5. **先写英文，再写中文，并核对对等性**：用模板起草完整英文；散文按英文习惯写。再基于**同一份事实清单**写完整中文：先同步事实、章节与视觉结构，再组织中文表述，不要把英文逐句硬译后再回头改命令或编号。
6. **清理后对照检查**：删除未启用的 OPTIONAL 整块（含注释外壳），并去掉模板里剩余的说明性 HTML 注释，不要把注释外壳留给用户。去掉空节与未替换占位符（待核对草稿可保留编辑用 `{{TODO: ...}}`）。确认正文直接从摘要起笔，未出现版本号标题、项目名标题、发布日期/类型/上一版本等冗余头部，也无语言标题或切换链接；两侧章节（均为 `##`）与事实一一对应、无密钥、无编造链接或校验和。
7. **交付正文与简短交付说明**：明确交付状态；交付说明按第 9 节列出 Tag 对比范围、已启用与省略的章节及原因、未验证命令或 `{{TODO}}`、需维护者重点核对的风险点。

在本规范仓库根目录运行成稿检查，将文件路径替换为实际的双语正文路径。

```bash
python3 releases/scripts/check-release-docs.py release /path/to/release.md
```

预发布正文追加 `--prerelease`，要求两种语言的摘要后都有警示。含编辑用 TODO 的待核对草稿追加 `--draft`。预发布草稿可同时使用两个参数。定稿时去掉 `--draft` 再检查。对于直接粘贴的 PR 地址，人工核对两侧的仓库和编号。

交付说明标明「可发布成稿」或「待核对草稿」。次要未知内容可省略；关键事实缺失时交付草稿，例如已确认破坏性变更但迁移方法未知，应保留影响说明并标出待核对项。可发布成稿须清除所有编辑用 `TODO` 和模板占位符。

---

例如拟发布的补丁已固定目标提交并核实修复，计划稍后上传安装包。正文可写修复结果，交付说明可记「文案可发布，版本待公开，上传后核对下载入口和公开日期」。若主升级路径仍不清楚，交付待核对草稿。

## 3. 章节清单

### 必需（每次发布都要有；缺事实则删或改写，不要编）

| 章节 | 写什么 |
|---|---|
| 版本摘要 | 正文直接从英文摘要起笔，`---` 之后直接写中文摘要。各用一句短句概括本次最重要的功能或修复，直接写出用户可见的变化。须来自真实变更，禁止“重大升级、全面优化”这类空话。不要加项目名或版本号标题，不要加发布日期、版本类型或上一版本等冗余头部，也不要加 “English / 中文” 标题或语言切换链接。 |

版本摘要不可省略；事实不够时在待核对草稿中用 `{{TODO: ...}}` 并在交付说明中列出，不要编造。项目名、Tag / 版本号由 GitHub Release 页面展示，不必在正文中重复。

### 条件章节（无证据必须整块删除，不可无证填写）

| 章节 | 仅在以下情况启用 |
|---|---|
| 预发布 / 重要提示 | 本版本是 Pre-release（`alpha` / `beta` / `rc` 等）；或确有必须让用户先看到的升级风险、破坏性变更警示。使用 GitHub 原生 `WARNING` / `IMPORTANT`，不要把普通摘要放进提示块。 |
| 亮点视觉 / Demo | 本次发布已有真实截图、GIF，或可核实的命令输出。按第 5 节保持紧凑，不要用占位图，不要编造输出或基准数据。启用时使用 `## Highlights` / `## 亮点展示`。它不属于变更分类。有破坏性变更时放在该节之后、其他变更分类之前；否则放在摘要和必要警示之后。双语都启用时两侧都要有这一节和同一图片地址。检查器比较该节图片地址；只有一侧有图会失败。Added、Fixed、Security 的完整先后仍按模板人工核对。 |
| 破坏性变更 | 本版本确有不兼容改动。须写清影响范围与迁移步骤；步骤未知则标 `{{TODO}}`。本节应紧跟摘要（及必要警示）之后，不可淹没在新功能后面。 |
| 新增功能 | 确有已落地、用户可见的新能力。写成具体收益，不要口号，也不要把未合并的路线图写成已发布功能。 |
| 行为变更 | 确有用户可观察的行为变化，或有证据的性能、体验或可靠性改进。可以写效果，但不得夸大或编造数字。推荐标题是「行为变更」。检查器也接受别名「优化与改进」，并把它当成 Changed。 |
| 问题修复 | 确有已修复的缺陷。写清现象与触发条件，并在存在真实编号时引用 Issue / PR。 |
| 安全修复 | 已核实、且有公开披露依据的安全修复或公告。公开措辞与范围见第 8 节。 |
| 弃用与移除 | 确有弃用或删除的 API、标志、配置、文件或行为。说明替代方案（若已存在）。 |
| 维护与依赖更新 | 依赖、工具链、CI 或文档等维护性变更，且对使用者或集成方有必要知晓。纯内部琐碎提交可省略。 |
| 安装与升级 | 仓库确有安装/升级途径，或本次 Release 附带真实产物。**主安装/升级路径必须展开**。只写仓库真正支持的方法。 |
| 已知问题 | 本版本已确认、仍未解决的限制或缺陷。不要为了“看起来严谨”编一套问题列表。 |
| 贡献者 | 能核实的、在本 Tag 范围内有贡献的 GitHub `@handle`。不要编造致谢，也不要罗列无关机器人账号，除非维护者惯例如此且可证实。两侧 `@handle` 集合必须相同，检查器会比较。 |
| 完整变更日志 | 按第 7 节核实同一包的可比基线、目标引用及 Compare URL，并核对发布线或既定升级路径。链接可见文字用 “Full Changelog” / “完整变更日志”，不要在正文中重复写版本号。首次发布见第 7 节：不要虚构上一版本。 |
| 折叠块 (`<details>`) | 仅用于次要的长内容，例如完整提交列表、多平台下载表、SHA256 校验和。不可折叠核心变更条目或主升级入口。 |

### OPTIONAL 块如何处理（避免把“可启用”当成“应留下”）

模板里用 HTML 注释包起来、并标为 `OPTIONAL` 的块：

- **启用：** 去掉包围的 `<!--` 与 `-->`，填入已核实的真实内容，并删除模板说明文字。不要把注释外壳留在用户可见的 Release 正文里。
- **不需要或无证据：** **整块删除**（含标题、示例标记和注释本身）。不要给用户留下空标题、`None` / `无`、`TBD`、未替换的 `{{PLACEHOLDER}}`，或一大段未解开的 OPTIONAL 注释。
- 模板中出现某个块，并不表示默认启用。内部待确认只用 `{{TODO: ...}}`，并在交付说明中列出。

## 4. 按版本类型与项目类型裁剪

先按**版本类型**决定语气、必读信息和章节密度，再按**项目类型**决定安装/升级与产物该怎么写。两者同时生效：例如库的 Major 预发布，既要有预发布警示和迁移说明，也要写真实的包管理器升级方式，而不是应用商店安装包。

### 4.1 按版本类型

**首次发布（Initial Release，如 `v0.1.0` / `v1.0.0`）**

- 内容突出：这是什么、核心能力、如何安装或开始使用。可用「新增功能」承接首发能力列表。
- 不要假装存在上一版本的对比，也不要编一套“修复了以往问题”的列表。
- 完整变更日志：删除 Compare 上一版本的链接；若需要，改为指向真实的 Tag 页或提交历史。

**大版本（Major）**

- 内容突出：不兼容改动必须紧跟摘要与必要警示之后；迁移步骤必须可核实，否则标 `{{TODO}}`。然后再写新能力与其他变更。
- 若有弃用或移除，不可遗漏。
- 不要把破坏性变更放在长长的新功能列表后面。

**常规功能版本（Minor）**

- 内容突出：用户可见的新能力与改进。
- 没有破坏性变更、安全修复或弃用时，这些章节一律删除，不要写 `None`。
- 保持精炼，不要为了“像大版本”而拉长。

**补丁 / 热修复（Patch / Hotfix）**

- 内容突出：修了什么、影响谁、如何升级。正文应短。
- 不要强行凑齐新增功能、演示图或其他无关章节。若确是紧急修复，在交付说明中标明 `Hotfix`，正文保持精简，不要另写版本类型或版本号标题。

**预发布（Pre-release：`alpha` / `beta` / `rc`）**

- 必须在英文与中文的摘要之后紧接 GitHub 原生 `WARNING` 警示块，说明当前为预发布、主要用于测试与反馈、不建议用于生产（除非维护者另有可核实的书面说明）。
- 预发布身份用警示块和交付说明标明即可；不要在正文里另写 Type 或版本号标题。GitHub 发布设置中的 Pre-release 标记由维护者负责。
- 变更仍须如实、可核实；不要因为是预发布就把未完成项写成已交付功能。

### 4.2 按项目类型

**CLI / 工具**

- 内容突出：新增或变更的命令与标志、行为变化、升级或安装命令；若有二进制附件，只列真实资源。
- 通常不要放：库的 import 示例、与本次发布无关的完整 API 清单。

**库 / SDK**

- 内容突出：API 与兼容性变化（须有证据）、包管理器升级方式、破坏性 API 的迁移。
- 通常不要放：生产部署手册、与库使用者无关的应用商店包或桌面安装包。

**Web 应用 / 服务**

- 内容突出：用户可见行为、配置或环境变量**名称**的变化、如何升级或部署该版本、如何确认已在运行（仅当真实健康检查或 URL 存在）。
- 环境变量只列名称与用途；示例值必须是占位符。

**桌面或移动应用**

- 内容突出：用户可见改动、系统要求变化（须有证据）、各平台安装包（仅列本次实际附件或已核实的分发入口）。
- 不要编造未提供的平台包、商店链接、签名或校验和。

**自动化工具**

- 内容突出：输入、执行方式或产物的变化，以及已有流水线如何升级。
- 展示优先：真实的输入/产物变化，而不是抽象功能口号。

**模板 / Skills 仓库**

- 内容突出：新增或变更的模板/技能、如何采纳本次更新、一个典型调用变化（须有证据）。
- 不要编造未提供的技能列表或参数。

## 5. 视觉与表达规范

目标是**简洁的开源项目风格**：统一的是品质，不是每次发布都把模板章节填满。先识别版本类型、项目类型和主要使用者，再选择必要章节与至多一种真实展示；不要套同一排徽章、大横幅或动效。

### 5.1 首屏

正文直接从摘要起笔。项目名与版本号由 GitHub Release 页面展示，不必在正文开头重复，也不要添加发布日期、版本类型、上一版本、 “English / 中文” 语言标题或中英文切换链接。

英文与中文各自按以下顺序开篇，正文仍按完整英文、`---`、完整中文排列：

1. 一句话功能或修复摘要。
2. 如有预发布或重要升级风险，紧接着摘要给出原生提示块。
3. 如有破坏性变更，紧接摘要及必要警示说明影响范围和迁移步骤。
4. 若确有真实截图、GIF 或已核实输出，可在上述内容之后放一份紧凑的亮点展示。

让人一眼看到“这次改了什么、值不值得升级、有没有风险”，比一眼看到很多装饰更重要。不要用大幅图片、过长概述、徽章墙或居中大横幅，把摘要和破坏性变更推得过远。

### 5.2 正文更易读

- 摘要只用一句短句，先给结果，再给分类变更。
- 改动写清“解决了什么 / 带来什么变化”。不要直接粘贴原始 commit message（如 `fix typo`、`wip`、`merge branch`），也不要把多个无关改动挤在一条里。
- 功能与修复写成具体收益或具体现象，且必须属实。禁止夸大性能或稳定性。
- 段落要短：一段讲一件事。对比信息或发布产物用表格，迁移与升级步骤用编号列表。
- 仅在预发布警示、破坏性变更或重要升级注意事项时，使用 GitHub 原生提示块（`> [!WARNING]`、`> [!IMPORTANT]`，必要时也可用 `> [!NOTE]`）。提示块的类型、数量和顺序两侧必须一致，检查器会比较，只在一侧出现会失败。不要把普通介绍放进提示块，也不要到处加粗。
- `<details>` 只折叠冗长的次要内容（完整提交列表、多平台下载表、SHA256 校验和等）。**核心变更条目与主升级入口必须展开，不可折叠。**
- 默认使用 GitHub 原生 Markdown；仅在必要时使用简单 HTML（如 `<details>`）。克制使用 emoji：模板标题不强塞多余 emoji，启用后也保持克制一致。禁止大横幅、装饰动画、无意义的分隔线堆砌、居中排版或访问计数器。
- 不要使用 `## English` 或 `## 中文` 作为语言分区标题，也不要添加语言切换链接。英文侧与中文侧的章节标题统一使用 `##`（例如 `## Added` 对 `## 新增功能`），不要在 `#` 之后直接跳到 `###`。

### 5.3 图片、附件与校验和

- 图片使用描述性 alt 文本，说明图里是什么，不要只写 “screenshot” 或 “demo”。
- 优先使用项目中已有、或本次发布已核对的资源；避免依赖不稳定的外部图床。不要生成 Logo，不要伪造界面或终端画面。
- 文件名、下载链接、体积与 SHA256 只写实际存在且已核对的值。缺校验和就省略该列或该行，不要编造哈希。
- 确保在浅色、深色主题和窄屏下仍可读：不要让关键升级信息只出现在过宽的图或必须横向滚动的表里。

### 5.4 双语视觉一致

中英文保持相同的视觉层级与信息结构：同一套开篇结构（均从摘要直接起笔）、同一组已启用章节、同一组条目、同一组命令、链接与演示资源。不要加语言分区标题、切换链接、版本号标题或冗余发布元信息。分节标题按语言本地化，并统一使用 `##`（例如 `## Added` 对 `## 新增功能`）。若使用文内锚点，必须跟**各自标题**走。不要把一种语言的分节锚点复制到另一侧，也不要只在一侧补充事实。

## 6. 双语编写与对齐规则

- **顺序固定：** 完整英文在前，`---` 分隔，完整中文在后。不要中英逐条交错，也不要改成两份独立文件。不要单独注明 “English / 中文”，也不要添加中英文切换链接。不要在正文中写版本号标题或重复项目名、发布日期、版本类型、上一版本等元信息。
- **事实完全一致：** PR / Issue 引用、贡献者 `@handle`、命令、共享文件路径与 URL、资源名与校验和必须两侧相同。禁止一侧多写一条变更、一个编号或一条命令。若安装或升级命令因仓库真实写法而带有版本参数，两侧命令必须一致，但不要为此另加版本号标题。
- 产物、PR、Issue、校验文件等共享引用指向同一目标；本页锚点和同主题的官方本地化文档可使用等价地址，例如英文 `#quick-start` 对应中文 `#快速开始`，英文迁移指南可对应同主题的官方中文版。
- **行文各自地道：** 英文用简洁、自然的开源变更日志写法；中文用准确、自然的简体技术表达。不要生硬直译，也不要为了句子一一对应而写出别扭译文。
- **标识符保持原文：** 命令、标志、代码标识符、文件名、API、包名、Tag、`@handle` 与 Issue/PR 编号不要翻译。
- **占位符约定：** 模板使用显式 `{{PLACEHOLDER_NAME}}`。交付给用户的 Release 正文中不应残留未替换的占位符。编辑用 `{{TODO: ...}}` 仅可留在待核对草稿。
  - **两边必须相同**的值：命令、代码标识符、共享文件路径与 URL、校验和、PR/Issue 编号、贡献者 handle。不要为了对齐而在正文两侧补写版本号或项目名。
  - **按语言分别填写**的值：版本摘要、变更说明、迁移步骤的叙述、图片 alt、`<details>` 的摘要、提示块正文等散文。
- 中英文已启用章节的集合必须一致；一侧删除某节时，另一侧也要删除。

## 7. Tag 范围、Compare 链接与引用规范

### 7.1 版本与基线

本小节是稳定版升级路径与维护线基线的权威版本。CHANGELOG 规范第 4 节第 1 条只保留这部分的摘要并指向这里；按 RC 记录习惯选取的 CHANGELOG 增量基线仍以第 4 节第 2 条为准。修改时两处同步。

- **版本与范围** 选择同一包、同一发布线的上一可比版本，预发布转正式版依下一条确定稳定升级路径，并核对基准引用与目标引用之间实际交付的改动。例如发布 `v1.9.4` 热修复时，查 `1.9.x` 维护线的上一可比版本，即使 `v2.0.0` 的发布时间更近。版本号和 Tag 原样保留，只有项目采用 SemVer 时才据其规则判断 Major、Minor、Patch。
- **预发布转正式版** 正式版 Release 默认面向从同一包的上一稳定版升级的用户。若 `v1.9.3 → v2.0.0-rc.1 → v2.0.0` 是该包的既定升级路径，以 `v1.9.3` 为正式版基线，包含 RC 已落地且正式版仍生效的变更与迁移。若项目明确另设 RC 到正式版的升级路径，可补充该区间；正式版前没有稳定版时按首次正式发布处理，另列有证据的 RC 增量，并为适用的 RC 用户保留迁移说明。稳定版用户应能在正式版正文或已核实的迁移指南中找到完整迁移路径。与 CHANGELOG 一起交付时，在交付说明中分别列出各自采用的基线及理由。

对照示例中，稳定版 `v2.0.0` 公开于 11 月 26 日。虽然 `v1.9.4` 维护线补丁于 11 月 25 日发布，`v2.0.0` 的既定升级路径仍从 `v1.9.3` 开始，Release 保留在 `v2.0.0-rc.1` 引入的参数迁移。逐版记录 RC 的 CHANGELOG 比较 `v2.0.0-rc.1...v2.0.0` 并指向完整迁移说明。参见[双语 Release 示例](./examples/stable-after-rc.md)与[中文 CHANGELOG](../changelog/examples/CHANGELOG-rc-history-zh-CN.md)。示例数据与地址均为虚构。

### 7.2 发布日期

Release 正文不写日期，日期只进入交付说明。核实规则的权威版本在 [CHANGELOG 规范](../changelog/changelog-agent-instructions.md) 第 4 节第 3 条，修改时两处同步；要点如下：

- 按上述日期规则核对项目约定渠道的公开事件。项目以 Tag 公开为发布时，采用能证明该 Tag 首次公开日期的记录。只有标签对象时间时，日期留待核对。
- 按仓库约定时区换算为 `YYYY-MM-DD`，无约定时使用 `Asia/Shanghai`（UTC+8）。同一版本的双语文稿、Release 和 CHANGELOG 共用同一条日期证据和换算结果。
- 发布前准备时，公开日期记为「待公开」，在交付说明列出发布后需核对的日期和下载入口。目标提交、正文事实和必要的升级路径均已核实且不声称未公开产物已可用时，交付说明记「文案可发布，版本待公开」，正文不写日期；同一版本的 CHANGELOG 这时保持待核对草稿并保留 `{{TODO: 核实发布日期}}`，不要要求它为了和 Release 文案同时就绪而删掉该 TODO。日期核实后，在双语 CHANGELOG 和 Release 交付说明中记录同一天。
- 对于声称已公开却缺少日期证据的版本，交付待核对草稿并记录缺口。交付说明记录公开事件、来源、时区和回退原因（如有）。

### 7.3 Compare 链接

- **Compare 链接必须指向真实范围。** 典型形式为 `https://github.com/<owner>/<repo>/compare/<上一 Tag>...<当前 Tag>`，其中两个 Tag 都必须存在，并分别对应第 7.1 节选定的基线与目标版本。核对包、发布线或稳定升级路径及实际交付范围。把该 URL 作为链接目标；可见文字使用 “Full Changelog” / “完整变更日志”，不要在正文里重复写出版本号或 Tag。不要编造 owner/repo，也不要写不存在的区间。
- **首次发布没有上一版本时：** 不要虚构 `v0.0.0` 或任意起点 Tag。删除 Compare 链接，或改为指向真实的 Tag 页面 / 提交历史；并在交付说明中写明这是 Initial Release。正文仍然不要写版本号标题。

### 7.4 PR、Issue、提交与贡献者引用

- **PR、Issue 与提交引用必须可核实。** 使用仓库中真实存在的 `#123` 或完整引用；提交哈希须真实，且缩写长度保持一致。找不到对应编号就不要编一个，也不要把无关 Issue 挂上去。
- **贡献者 `@handle` 必须可核实。** 只感谢在本 Tag 范围内确有贡献的 GitHub 用户。不要猜测显示名背后的账号，不要把未参与本版本的人写进去。

## 8. 安装、升级与发布产物规范

- **只写仓库真实支持的方法，以及本次 Release 实际存在的附件或分发入口。** 不要根据“这类项目通常还能在 Homebrew / Docker / 某应用商店安装”去补写未经证实的渠道。若真实命令需要版本参数，使用仓库既有写法；不要为了在正文中展示 Tag 而额外写入版本号标题或编造版本参数。
- **主安装/升级路径必须展开。** 按实际渠道选择可复制的命令、可点击的下载或商店链接、编号步骤，也可组合。若安装包是唯一升级途径，直接展示主下载入口。补充平台、完整资产表和校验信息可折叠。
- **命令必须来自仓库文档、发布工作流或可核对的注册源。** 若你未能实际执行，须在正文中标明“未在本环境验证”，并在交付说明中列出原因。不要假装已经验证，也不要改写未经证实的参数。
- **若该版本尚未真正发布到注册源或附件尚未上传：** 不要把安装命令写成已经可用。若渠道和主安装或升级方法均已核实，正文可写“包发布完成后使用……”，交付说明列出公开后应复核的入口。若必要的命令、分发渠道或主升级路径仍未知，交付待核对草稿并用 `{{TODO: 核实主升级路径}}` 标明缺口。
- **涉及破坏性变更时，必须提供可核实的迁移步骤。** 写清谁会受影响、要改什么、按什么顺序操作。步骤不完整或无法从仓库证实时，保留 `{{TODO}}`，不要用含糊的“请注意兼容性”代替。
- **产物表只列真实文件。** 文件名、平台、下载链接、体积、校验和缺哪一项就省略哪一项，绝不编造 SHA256 或下载 URL。
- 升级示例中不得出现真实密钥；配置或环境变量只写名称与用途，值用明显占位符。

## 8.1 Release 页面预览

预览目标 GitHub Release 页面，核对图片和文档链接可用且指向该版资源；无预览时优先核对固定到本次 Tag 或提交的资源地址，或已核实的该版附件链接。在交付说明记录验证结果。

## 8.2 安全披露

公开稿仅使用维护者已公开或明确批准对外披露的影响范围、修复版本、处理方式和公告链接。内部修复证据单独用于核实事实；披露范围待确认时，在交付说明提出待确认项。安全条目省略利用步骤和未经证实的 CVE 或严重级别。

正文结论必须有证据支撑：某版本已修复某问题，须核对修复已进入目标 Tag 或提交并核对实际行为；某产物可下载，须有目标版本实际公开的附件或分发记录；性能提升 X%，须有可追溯的版本、测量条件和结果。完整证据表以 [CHANGELOG 规范](../changelog/changelog-agent-instructions.md) 第 3.2 节为准。

## 9. 交付说明要求

Agent 交付 Release Notes 时，在**正文之外**另附一段简短交付说明（不要写进 GitHub Release 正文）。至少包括：

1. **版本和交付状态：** 标题、当前版本或拟用标识、上一可比版本（或首次发布）、比较区间与可核实的 Compare / Tag URL（无 Tag 时记录目标提交）、公开日期来源与时区（待公开时记为待核对），以及文案状态（可发布成稿、文案可发布且版本待公开，或待核对草稿）和发布状态（待公开、已公开或待核实）。版本待公开时写明对应 CHANGELOG 仍保留日期 TODO。
2. **已启用与省略的章节及原因：** 列出实际保留的章节；对模板中未启用的主要 OPTIONAL 块，用一句话说明省略原因（无此类变更、无附件、无真实演示等）。
3. **未验证命令或 `{{TODO}}` 项：** 哪些安装/升级/迁移命令已验证，哪些只是摘自仓库但未在本环境执行，以及正文里残留的 `{{TODO}}` 及其原因。
4. **需维护者重点核对的风险点：** 例如可能遗漏的破坏性变更、迁移步骤不完整、包尚未发布到注册源、校验和未提供、预发布文案是否足够醒目、日期时区依据，或发现但未写入正文的疑似密钥。

交付说明要短、具体、可执行，不要重复粘贴一整份 Release 正文。
