# 项目整体 CHANGELOG — Agent 执行规范

本文是给 Agent 的执行规范，**不是**给仓库用户看的变更日志正文，也不是为某个虚构仓库填写的示例 CHANGELOG。

当需要为 GitHub 上的真实项目编制、补全或更新**项目整体变更日志**时，先读完本文件，再按其中的工作流、证据要求，以及同目录下的版本节模板产出可交付文稿。把本规范与两个版本模板一并复制后，供后续 Agent 直接阅读使用即可。不要把 `*-template.md` 或本规范的文件名写进变更日志正文。

同目录配套模板：

- [`changelog-version-template.md`](./changelog-version-template.md) → 单个已发布版本的**英文稿**，写入 `CHANGELOG.md`（或仓库既有的英文变更日志）
- [`changelog-version-zh-CN-template.md`](./changelog-version-zh-CN-template.md) → 单个已发布版本的**中文稿**，写入 `CHANGELOG-zh-CN.md`（或仓库既有的中文变更日志）

文件开头、`Unreleased` 节和正文清理规则仍见第 8 节；不要把版本模板误当成完整 CHANGELOG 文件。

配套关系（供判断，不要混用规范）：

- 仓库介绍文档（`README.md` / `README-zh-CN.md`）应另按 README Agent 规范编写。
- 某一次 GitHub Release 的描述框正文应另按 Release Notes Agent 规范编写。
- **本文只约束仓库内的项目整体 CHANGELOG**（通常是 `CHANGELOG.md`，以及仓库已有的中文对应文件）。

---

## 0. 任务目标与非目标

**目标：** 依据仓库与 GitHub 上可核对的记录，为指定范围写出面向使用者的项目整体变更日志：版本（或时间）边界清楚、分类清楚、用户影响清楚、事实可追溯。

**非目标：**

- 不要把它写成 README、贡献指南、路线图或发布公告稿。
- 不要在未受权时创建 Git Tag、GitHub Release、提交、推送或代为发布。
- 不要为了演示格式而编造项目、版本、日期或变更条目。
- 不要把“ReadMe”理解成某家文档 SaaS；本任务不需要安装任何此类插件或服务。

## 1. 输入、产出与边界

### 1.1 动笔前必须确认的输入

先从仓库和任务说明核实以下输入，包括默认分支、文件位置、现有语言与标题格式。只有范围、语言、交付意图或授权仍有歧义时才询问。关键事实无法核实时，在交付说明里用 `{{TODO: ...}}` 标明；**不要自行假定后直接写成定稿。**

1. **仓库身份：** `owner/repo`、默认分支、当前要依据的 Git 引用（分支、Tag 或提交）。不要编造 owner/repo。
2. **覆盖范围：** 默认是**整个项目**——根目录、全部子包/模块、应用、脚本、面向用户的文档与发布配置都要审阅。若用户把范围收窄到某一个子包或目录，在交付说明中写明边界，并在文稿标题或引言中如实反映，不要把局部变更写成全项目变更。
3. **版本或时间范围：** 例如「未发布变更（Unreleased）」「某个 Tag 相对同一包、同一发布线的上一可比版本」「某两个日期之间」「从初始版本到当前的完整历史」。范围必须能由 Tag、提交或用户指定的边界证实。用户仅指定起止日期时，默认按项目发布时区筛选窗口内公开的版本，含首尾两天，每版仍按完整可比基线整理。若明确要求只列窗口内发生的改动，在交付说明记录采用的事件、时区、首尾边界及引用；以注明范围的期间摘录单独交付，不能覆盖完整历史版本节。
4. **已有约定：** 现有 `CHANGELOG` / `HISTORY` / `CHANGES` 的文件名、位置、语言、章节标题、版本标题格式、是否已按某种已公布规范编排。
5. **语言要求：** 用户是否要求中英双语；仓库是否已有中英文两份变更日志。
6. **交付形态：** 只交草稿，还是同时准备可粘贴的 GitHub Release 正文。若同时要写 Release 正文，CHANGELOG 仍按本文；Release 正文改走 Release 规范，不要把两套版式混在同一份稿里。

例如某个补丁在 11 月 9 日合入修复、11 月 12 日公开。整理「11 月 10 日至 20 日发布的版本」时包含该补丁的完整用户变更；整理「这段时间合入的改动」时该次合入不在摘录范围内。

### 1.2 标准产出

每次交付两样东西，且必须分开：

1. **变更日志正文：** 用于仓库变更日志文件的 Markdown（新建、更新某一版本节，或按要求整理完整历史）。
2. **正文之外的交付说明：** 说明审阅范围、版本/时间边界、证据来源、启用与省略的分类、未核实项、需要维护者确认的风险。不要把交付说明写进 CHANGELOG 正文。

交付说明标明「可发布成稿」或「待核对草稿」。次要未知内容可省略；关键事实缺失时交付草稿，例如已确认破坏性变更但迁移方法未知，应保留影响说明并标出待核对项。可发布成稿须清除所有编辑用 `TODO` 和模板占位符。

### 1.3 明确边界（未获点名授权就不得做）

- 不修改仓库、不创建分支、不提交、不推送、不打 Tag、不创建或编辑 GitHub Release、不合并 PR、不评论、不联系外部贡献者或用户。
- 不把草稿当成已经发布的版本历史。
- 不写入真实密钥，也不把仓库里疑似泄露的密钥抄进 CHANGELOG。
- 正文只写已核实的用户可见变化；内部重构、排版和无效合并提交若对使用者无影响，应合并或省略。

## 2. 硬性规则

1. **先做全项目审阅并收集证据，再写正文。** 事实以当前仓库和 GitHub 上可核对的记录为准，不以记忆、习惯用法或同类项目的常见写法为准。
2. **禁止编造。** 不得虚构或“合理推测”以下任何一项：
   - 项目名称、版本号、Git Tag、发布日期、版本类型（`Stable`、`Pre-release`、`Hotfix` 等）
   - 变更内容、影响范围，以及性能、体积或其他基准数据
   - PR / Issue 编号、Compare 链接、提交哈希、贡献者 `@handle`
   - 安装、升级、迁移命令，以及最低运行环境变化
   - Release Assets 的文件名、大小、平台、下载链接或 SHA256 等校验和
   - 截图、GIF、终端输出、演示地址或未经验证的命令结果
   - 安全公告编号、CVE、已知问题列表
   - 许可证、徽章、维护状态等与变更无关、却可能被顺手写入的信息
3. **未知就不写。** 查不到或不确定时：删除该可选章节；若位置几乎必需但事实未知（例如确有破坏性变更，但迁移步骤写不全），在稿中用 `{{TODO: 缺少什么、为什么不能确定}}` 标记，并在交付说明里汇总。禁止用“可能”“大概”“通常是 `npm i package@latest`”填空。
4. **按范围、版本类型与对用户的影响裁剪。** 只启用有证据且对该版本、该类使用者有用的分类。不要为了模板完整或“看起来全面”而堆砌空节，也不要写 `None` / `无`。
5. **面向使用者改写，不要照搬原始 commit 标题。** 写清“解决了什么 / 带来什么变化”。丢弃 `fix typo`、`wip`、`merge branch` 这类对使用者无意义的记录；把零碎、重复或仅内部的提交合并为清晰条目。
6. **双语同步事实，行文各自地道。** 若产出中英文，必须共用同一套事实、PR/Issue 引用、命令、共享资源路径和 URL、版本号和校验和。先同步事实与结构，再按各自语言习惯书写，不要生硬直译。命令、标志、代码标识符、文件名、API、包名、Tag、`@handle` 与编号保持原文，不要翻译。
7. **严禁密钥。** 不得写入真实 API key、token、密码、私钥、证书，或连接字符串中的密钥部分。示例只用明显占位符（如 `YOUR_API_KEY`、`$API_TOKEN`）。若提交说明、示例或附件里已经出现疑似密钥，不要复制进 CHANGELOG，并在交付说明中提醒维护者轮换。
8. **命令、链接与引用必须可执行或可核对，否则标明未验证。** 不要写找不到入口的伪命令，也不要改写未经证实的参数。Compare 链接、PR/Issue、Tag、校验和都必须真实存在。
9. **安全相关条目只写已核实的影响与修复方式。** 不写利用步骤，不编造 CVE 或严重级别。公开稿仅使用维护者已公开或明确批准对外披露的影响范围、修复版本、处理方式和公告链接。内部修复证据单独用于核实事实；披露范围待确认时，在交付说明提出待确认项。

## 3. 全项目审阅与证据要求

CHANGELOG 必须来自全项目审阅，而不是只看最近几次 commit 标题，也不是只看某一个目录。

### 3.1 必须核对象

按实际存在的对象阅读，不在项目里的不要虚构：

- 现有变更日志、GitHub Releases / Release 草稿、发布说明
- 全部相关 Git Tag 与发布时间、Tag 注解、默认分支历史
- 指定范围内的 commits、已合并 PR、关联 Issue、讨论中已被维护者确认的结论
- 根目录与各子包的版本清单（如 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、Chart/配方版本）
- 面向用户的文档、迁移说明、`SECURITY.md`、已发布安全公告
- CI 发布工作流、实际 Release Assets 与校验和（如有）
- 该范围内真实支持的安装或升级方式（仅当正文需要写升级/迁移时）

### 3.2 证据标准

- 每一条变更都应能指回能支持该条结论的证据。普通条目可保留轻量引用。
- 有真实 PR / Issue 编号时一并引用，形式与仓库既有习惯一致（通常为 `#123`）。找不到就不要编一个，也不要把无关 Issue 挂上去。
- 提交哈希若使用，必须真实，缩写长度保持一致。
- 贡献者 `@handle` 必须能在该范围内核实。不要猜测显示名背后的账号，不要感谢未参与该范围的人，也不要默认罗列机器人账号，除非维护者惯例如此且可证实。
- 性能、体积、兼容版本、平台支持必须有记录或可复现依据。没有数字就不要写数字。

| 正文结论 | 需核对的证据 |
|---|---|
| 某版本已修复某问题 | 修复已进入目标 Tag 或提交，并核对实际行为。Issue 可补充问题背景。 |
| 某产物可下载 | 目标版本实际公开的附件或分发记录。CI 工作流可辅助核对构建。 |
| 性能提升 X% | 对应版本、测量条件和结果可追溯。 |

### 3.3 全项目视角的特别要求

- **多包 / monorepo：** 列出范围内的全部包或模块，检查是否有独立版本或独立发布。若各包版本不一致，按仓库既有方式分组书写，或在交付说明中说明无法合并为单一版本线，不要把只属于一包的 breaking change 写成全仓库 breaking change。
- **文档、示例、CI、构建链：** 仅当对使用者、集成方或升级过程有必要知晓时写入「维护与依赖更新」；纯内部琐碎改动省略。
- **未发布工作：** `Unreleased` 只收已进入指定目标分支、且尚未包含在该包与发布线的上一版本中的变更。未合并 PR、其他分支的候选改动和路线图计划可按用户要求另写发布规划草稿。
- **核对最终交付行为：** 在分类前对照本次目标与上一公开版本。范围内新增后完整回滚且从未交付的改动可省略；部分回滚只写最终生效部分；撤回上一公开版本已有的功能时记录用户影响。多个 PR 共同完成一次修复时合并成一条，并保留必要引用。
- **冲突处理：**
  - 旧 CHANGELOG 与 Git/PR 记录不一致：以可核对的 Git、Tag、已合并 PR 和能证实的发布记录为准，并在交付说明中指出差异，不要悄悄改写历史口吻而不说明。
  - 多个来源对同一改动描述不同：采用能被代码和 PR 证实的那一版，避免叠加夸张措辞。
  - 只有 commit 标题、看不出用户影响：继续查 PR、diff 或文档；仍看不清就标 `{{TODO}}` 或省略，不要臆造收益。

## 4. 版本与时间范围

版本线和时间盒是 CHANGELOG 的骨架，必须先定范围再写条目。

1. **范围必须可证实。** 选择同一包、同一发布线的上一可比版本，预发布转正式版依第 2 条确定基线，并核对基准引用与目标引用之间实际交付的改动。例如发布 `v1.9.4` 热修复时，查 `1.9.x` 维护线的上一可比版本，即使 `v2.0.0` 的发布时间更近。版本号和 Tag 原样保留，只有项目采用 SemVer 时才据其规则判断 Major、Minor、Patch。用户指定时间范围时，使用可证实的日期或提交边界。
2. **沿用项目既有版本与 Tag 格式。** 包括日期版本、自定义前缀及预发布后缀。若项目逐版记录同一包和目标版本线的 RC，以已记录的上一 RC 为正式版增量基线，保留稳定版升级所需的完整迁移入口（例如正式版 Release、迁移指南或相应历史节）。若项目不逐版记录 RC，则以已核实的上一稳定版作为基线，纳入正式版仍生效的 RC 期间改动。没有上一稳定版时按首次正式发布处理；若已逐版记录 RC，仍可记录有证据的 RC 增量。与 Release 一起交付时，分别注明两个基线与选择依据。
3. **核实发布日期。** 先确定仓库或子包约定的发布渠道与公开事件。以 GitHub Release 为准时取公开发布时间，以包注册源为准时取该包的实际公开发布时间。对应记录缺失时，只有项目明确以公开打标作为发布事件、能核实 Tag 已公开，且附注标签（annotated tag）的打标时间可核实时，才按该惯例使用打标时间。轻量标签（lightweight tag）没有独立打标时间；目标提交的作者或提交时间、仅存在于本地的 Tag，以及无公开打标惯例的附注标签时间均不可作为发布日期。日期证据不足时交付待核对草稿，并标注 `{{TODO: 核实发布日期}}` 或在交付说明中记录缺口。按仓库约定时区换算为 `YYYY-MM-DD`，无约定时使用 `Asia/Shanghai`（UTC+8）。同一版本的双语文稿、Release 和 CHANGELOG 共用同一条日期证据和换算结果。交付说明记录公开事件、来源、时区和回退原因（如有）。
4. **`Unreleased` 与已发布版本必须分开。** 符合第 3.3 节的未发布内容写入 `Unreleased`（或仓库既有的等价节）。应用户要求预拟某一版本时，作为待核对草稿交付并注明尚未发布。
5. **首次发布没有上一版本时：** 不要虚构 `v0.0.0` 或任意起点 Tag，也不要编一套“修复了以往问题”的列表。完整对比链接删除，或改为指向真实的 Tag 页 / 提交历史，并在交付说明中写明这是 Initial Release。
6. **整理完整历史时：** 按已核实的公开发布记录逐个版本编写，旧版本不要用现在的口吻改写事实。某个历史版本缺少资料时，保留已核实部分并标 `{{TODO}}`，或在交付说明中声明该版本无法复原，禁止用猜测补完。
7. **版本类型只用于裁剪语气和必读信息**（见第 5.3 节）。类型本身写入交付说明；是否在正文里写 `Pre-release` / `Hotfix` 等标签，跟随仓库既有 CHANGELOG 习惯，没有习惯就不要为了形式另加一层装饰性标签。

在[逐版记录 RC 的示例](./examples/CHANGELOG-rc-history-zh-CN.md)中，`v2.0.0` 比较 `v2.0.0-rc.1...v2.0.0`，并链接覆盖稳定版升级的[配套 Release 示例](../releases%20readme/examples/stable-after-rc.md)。Release 从既定路径的上一稳定版 `v1.9.3` 比较。维护线补丁 `v1.9.4` 单独比较 `v1.9.3...v1.9.4`。示例数据与地址均为虚构。

### 4.1 与 GitHub Release 正文的关键区别

GitHub Release 页面已经展示标题和 Tag，因此 Release 正文可以不重复项目名、版本号、日期和类型。**仓库里的 CHANGELOG 没有这一层界面衬托，每个已发布版本节都必须写清已核实的版本号和日期。** 不要把 Release 规范里“正文不写版本号标题”套用到 CHANGELOG。

## 5. 分类和用户影响

### 5.1 分类清单

采用「固定结构 + 按需分类」：版本标题、日期和一段摘要几乎每次都要有；其余分类无证据就整块删除。

**几乎每次都要有（缺事实则删或改写，不要编）：**

| 部分 | 写什么 |
|---|---|
| 版本标识与日期 | 已发布版本写已核实的版本号和 `YYYY-MM-DD`。未发布内容使用 `Unreleased`（或仓库既有等价标题），不要编造发布日期。 |
| 版本摘要 | 用 1–3 句说明该版本（或该时间范围）的核心目标与用户可见结果。须来自真实变更，禁止“重大升级、全面优化”这类空话。 |

**条件分类（无证据必须整块删除）：**

| 分类 | 仅在以下情况启用 | 英文标题 | 中文标题 |
|---|---|---|---|
| 预发布 / 重要提示 | 该版本是 Pre-release，或确有必须先看到的升级风险。使用 GitHub 原生 `WARNING` / `IMPORTANT`，不要把普通摘要放进提示块。 | （提示块，无单独标题也可） | 同左 |
| 破坏性变更 | 确有不兼容改动。写清影响对象与迁移步骤；步骤未知则标 `{{TODO}}`。必须紧跟摘要（及必要警示）之后，不可淹没在新功能后面。 | Breaking Changes | 破坏性变更 |
| 新增功能 | 确已落地、用户可见的新能力。写成具体收益，不要口号，也不要把未合并路线图写成已发布功能。 | Added | 新增功能 |
| 行为变更 | 确有用户可观察的行为变化，或有证据的性能、体验或可靠性改进。可以写效果，但不得夸大或编造数字。 | Changed | 行为变更 |
| 问题修复 | 确已修复的缺陷。写清现象与触发条件，有真实编号时引用 Issue / PR。 | Fixed | 问题修复 |
| 安全修复 | 已核实且有公开披露依据的安全修复或公告。 | Security | 安全修复 |
| 弃用与移除 | 确有弃用或删除的 API、标志、配置、文件或行为。若已有替代方案，一并说明。 | Deprecated & Removed | 弃用与移除 |
| 维护与依赖更新 | 依赖、工具链、CI 或文档等维护性变更，且对使用者或集成方有必要知晓。 | Maintenance & Dependencies | 维护与依赖更新 |
| 安装与升级 | 该版本的升级途径对使用者有必要单独说明，或附带真实产物。只写仓库支持且已核实的下载、商店链接、步骤或命令；主安装或升级路径必须展开。 | Installation & Upgrade | 安装与升级 |
| 已知问题 | 该版本已确认、仍未解决的限制或缺陷。不要为了“看起来严谨”编列表。 | Known Issues | 已知问题 |
| 贡献者 | 能核实的、在该版本范围内有贡献的 GitHub `@handle`。 | Contributors | 贡献者 |
| 完整对比 | 第 4 节选定的可比基线与当前 Tag（或等价范围）均可核对。可见文字用 “Full Changelog” / “完整变更日志”，链接指向真实 Compare URL。 | Full Changelog | 完整变更日志 |

若仓库已有稳定分类名称（例如已把 Deprecated 与 Removed 拆开，或使用其他已公布的章节名），**跟随仓库，不要为了套用上表而改写历史章节名。** 新写入的版本尽量与上表或仓库既有名称对齐，并保证中英分类集合一致。

### 5.2 用户影响怎么写

- 先写结果，再写必要细节。一条只讲一件对用户或集成方有意义的事。
- 功能与修复写成具体收益或具体现象，且必须属实。例如不要只写“修复登录问题”，而应写清在什么条件下出现什么现象、现已如何处理——前提是记录里确实如此。
- 破坏性变更要写清谁受影响、旧行为是什么、新行为是什么、如何迁移。不要用含糊的“请注意兼容性”代替。
- 把多个无关改动挤在一条里、或把内部重构打扮成用户特性，都视为不合格。
- 段落要短。对比信息或产物用表格，迁移与升级步骤用编号列表。

### 5.3 按版本类型裁剪

**首次发布：** 突出这是什么、核心能力、如何开始使用。可用「新增功能」承接首发能力。不要假装存在上一版本对比。

**大版本（Major）：** 不兼容改动必须紧跟摘要与必要警示；迁移步骤必须可核实，否则标 `{{TODO}}`。有弃用或移除不可遗漏。不要把破坏性变更放在长长的新功能列表后面。

**常规功能版本（Minor）：** 突出用户可见的新能力与改进。没有破坏性变更、安全修复或弃用时，这些节一律删除。

**补丁 / 热修复（Patch / Hotfix）：** 突出修了什么、影响谁、如何升级。正文应短，不要强行凑齐新增功能或其他无关分类。

**预发布（`alpha` / `beta` / `rc` 等）：** 紧接摘要启用 GitHub 原生 `WARNING`。若为双语，两种语言都必须启用。说明主要用于测试与反馈、不建议用于生产（除非维护者另有可核实的书面说明）。不要把未完成项写成已交付功能。GitHub 上的 Pre-release 标记由维护者设置，Agent 不得擅自发布。

### 5.4 按项目类型强调（不要写成 README）

在分类不变的前提下，按主要使用者选择该写细的内容：

- **CLI / 工具：** 命令与标志变化、行为变化、升级方式；有二进制附件时只列真实资源。
- **库 / SDK：** API 与兼容性变化、包管理器升级、破坏性 API 的迁移。
- **Web 应用 / 服务：** 用户可见行为、配置或环境变量**名称**的变化、如何升级该版本。环境变量只列名称与用途，值用占位符。
- **桌面或移动应用：** 用户可见改动、系统要求变化、各平台安装包（仅列实际附件或已核实的分发入口）。
- **自动化工具：** 输入、执行方式或产物的变化，以及已有流水线如何升级。
- **模板 / Skills 仓库：** 新增或变更的模板/技能、如何采纳更新；不要编造未提供的技能或参数。
- **混合 / monorepo：** 按用户路径或包分组，避免把互不相关的变更混成一条。

## 6. 推荐工作流

1. **确认输入与边界：** 仓库、全项目或子范围、版本/时间盒、已有 CHANGELOG 约定、语言与交付形态。
2. **全项目收集事实：** 按第 3、4 节列出 Tag / 提交范围、PR、Issue、子包版本、既有日志、发布产物与升级方式。先画出版本线和每个版本的证据清单，再动笔。
3. **判定版本类型与项目类型：** 按第 5 节决定必读信息和分类密度。不要默认启用全部可选分类。
4. **合并归类，面向用户改写：** 将范围内的变更归入第 5.1 节的分类，合并内部琐碎提交，丢弃对使用者无意义的记录。
5. **确定启用章节：** 只保留有证据且对该版本有用的分类。预发布必须有警示，双语稿的两种语言都必须启用；有不兼容改动必须有破坏性变更，并给出可核实的迁移步骤或 `{{TODO}}`。
6. **按仓库约定落稿：**
   - 已有 CHANGELOG：在既有文件结构上新增或修正指定范围，不无故改写无关的历史版本格式。
   - 尚无 CHANGELOG：用第 8 节及同目录版本模板新建。
   - 需要双语时，基于**同一份事实清单**写两种语言：先同步版本号、日期、分类、条目数量、编号和链接，再组织行文。
7. **清理后对照检查：** 删除未启用分类（含空标题），去掉模板说明性注释和未替换占位符（待核对草稿可保留编辑用 `{{TODO: ...}}`）。核对范围、事实、链接、无密钥、无越权发布用语。
8. **交付正文与简短交付说明：** 明确交付状态；交付说明按第 9 节书写。入库或发布按第 11 节的授权边界执行。

## 7. 文件约定、双语与版式（含冲突化解）

以下约定吸收了 README 规范与 GitHub Release 规范，但按「仓库内长期变更日志」这一载体做了取舍。不要把另外两份规范的版式硬套过来。

### 7.1 文件名与位置

- 默认写仓库根目录的 `CHANGELOG.md`。若仓库已有 `CHANGELOG.md`、`CHANGES.md`、`HISTORY.md` 或 `docs/CHANGELOG.md` 等既有文件，**沿用既有路径和文件名**，不要平行再造一份互相竞争的日志。
- 不要把本规范文件名，或 `*-template.md` 之类名称写进变更日志正文。

### 7.2 双语：何时分文件，何时单篇

- **仓库文档习惯（来自 README 规范）：** 根目录介绍使用两份独立文件，并在顶部用相对路径做语言切换。
- **GitHub Release 习惯（来自 Release 规范的最新约定）：** 单篇正文、完整英文在前、`---` 分隔、完整中文在后；**不要**单独注明 “English / 中文”，也**不要**加语言切换链接；两侧分类用 `##` 对等标题。
- **本规范对 CHANGELOG 的化解：**
  1. 用户未指定交付结构且仓库已有变更日志时，**跟随仓库**（单文件或 `CHANGELOG.md` + `CHANGELOG-zh-CN.md` 均可）。
  2. 需要新建、且用户要求双语时：默认采用两份独立文件，因为多版本长文档不适合把全部英文历史和全部中文历史对贴在同一篇里。
     - `CHANGELOG.md`：英文主文件
     - `CHANGELOG-zh-CN.md`：简体中文文件
     - 两份文件顶部使用相对链接，当前语言加粗：

       英文文件：

       ```markdown
       [**English**](./CHANGELOG.md) | [中文](./CHANGELOG-zh-CN.md)
       ```

       中文文件：

       ```markdown
       [English](./CHANGELOG.md) | [**中文**](./CHANGELOG-zh-CN.md)
       ```

     - 使用相对路径，便于 fork 与换分支后仍可用。不要把语言切换做成 GitHub 绝对 URL，也不要链到本规范文件。
  3. 交付结构按用户本次要求、仓库既有组织方式、新建默认方式依次确定。采用单篇双语时，已有单篇布局可沿用；新建单篇采用「英文在前、`---`、中文在后；不加语言标题和切换链接」。此时若是 Release 正文，版本号标题规则改走 Release 规范。
  4. 用户只要一种语言时，只维护那一份文件，不要为了形式硬补另一种语言。

在规范仓库根目录运行 `python3 scripts/check-release-docs.py changelog 文件路径` 检查单语言成稿；双文件追加中文文件路径；英文、中文以独立一行 `---` 分隔的单篇双语追加 `--bilingual`。其他既有排版按仓库惯例人工验收。

### 7.3 必须保留、不得硬套的版式

- **必须写版本号与日期**（已发布版本）。这是 CHANGELOG 与 Release 正文最重要的差异。
- **不要**把 README 的首屏、Logo、徽章墙、快速开始、目录装饰搬进 CHANGELOG。变更日志靠版本线和分类说话。
- 保持克制的开源风格：默认使用 GitHub 原生 Markdown；短段落；提示块只用于预发布、破坏性变更或重要升级注意事项；`<details>` 只折叠次要长内容（完整提交列表、多平台校验和等），**核心变更条目与主升级命令必须展开**。
- 不滥用 emoji、分隔线、居中排版、大横幅、访问计数器、图标墙或装饰动画。标题不强塞多余 emoji。
- 如需配图，必须是该版本已有的真实素材，使用描述性 alt，优先相对路径或项目已在使用的稳定 URL。没有素材就省略，不编造、不生成。
- 中英视觉层级一致：同一组版本、同一组已启用分类、同一组条目、同一组命令与链接。已发布版本节用 `##` 并注明版本和日期；其下分类用 `###`，并按语言本地化（`### Added` 对 `### 新增功能`）。这与 GitHub Release 正文不同：Release 没有版本标题，分类直接用 `##`。若使用文内锚点，必须跟**各自标题**走。

版本标题沿用既有格式，例如括号日期 `## v1.9.4 (2026-11-25)`，或 `## v1.9.4 - 2026-11-25`、`## [v1.9.4](URL) - 2026-11-25`，或 `## [v1.9.4] - 2026-11-25` 搭配文末 `[v1.9.4]: URL`。使用引用式链接时，为新增标题核对唯一、有效的定义。比较链接按惯例放一处；标题已指向比较时省略正文的同一链接。首发标题可指向真实 Tag 页。

### 7.4 可选块处理

同目录版本模板的每个 `OPTIONAL` 注释块都包含说明、对应标题（若有）和正文。

- **启用：** 去掉包围的 `<!--` 与 `-->`，填入已核实的真实内容，并删除模板说明文字。不要把注释外壳留给用户。
- **不需要或无证据：** **整块删除**（含标题、示例标记和注释本身）。不要留下空标题、`None` / `无`、`TBD`、未替换的 `{{PLACEHOLDER}}`，或一大段未解开的 OPTIONAL 注释。
- 模板中出现某个块，并不表示默认启用。内部待确认只用 `{{TODO: ...}}`，并在交付说明中列出。

## 8. 可复用输出模板

下面模板用于**仓库内 CHANGELOG**。占位符为 `{{NAME}}`。交付给用户的正文中不应残留未替换占位符。编辑用 `{{TODO: ...}}` 仅可留在待核对草稿。

- **两边必须相同**的值：版本号、日期、命令、代码标识符、共享文件路径与 URL、校验和、PR/Issue 编号、贡献者 handle。
- 产物、PR、Issue、校验文件等共享引用指向同一目标；本页锚点、适用的语言切换链接和同主题的官方本地化文档可使用等价地址，例如英文 `#quick-start` 对应中文 `#快速开始`，英文迁移指南可对应同主题的官方中文版。
- **按语言分别填写**的值：摘要、变更说明、迁移步骤叙述、图片 alt、`<details>` 摘要、提示块正文等散文。

文件开头可使用极简标题；不要加项目宣传语。若采用双文件双语，把语言切换放在标题下。

```markdown
# Changelog

<!-- 仅当使用 CHANGELOG.md + CHANGELOG-zh-CN.md 时保留对应切换行；单语言文件删除本行。 -->
```

可参照[英文](./examples/CHANGELOG.md)与[中文](./examples/CHANGELOG-zh-CN.md)双语成稿示例。示例使用虚构数据和格式演示链接。其中 `v1.9.4` 以 `v1.9.3` 为基线。假设 11 月 23 日打 Tag、11 月 25 日公开发布，两个交付物均采用 11 月 25 日。已随补丁发布的空字段修复写入补丁节，留在目标分支但未随版发布的分隔符功能继续放在 `Unreleased`。

### 8.1 未发布变更

```markdown
## Unreleased

{{RELEASE_SUMMARY}}

<!-- 无已核实的未发布变更时，不要保留空的分类标题。不要为 Unreleased 编造发布日期。 -->
```

中文对应标题为 `## Unreleased` 或仓库既有写法（可在其下用中文摘要）；不要把未发布内容写成虚构版本号。

实际发布后，将本次随版交付的条目移出 `Unreleased` 并归入该版本节，保留尚未随版交付且仍符合准入条件的内容。更新该版本和 `Unreleased` 的比较链接（如适用）。若同名版本节已存在，更新现有节；对同一版本重复执行后仍应只有一个版本节。双语两边同步检查重复、漏项和比较链接。

### 8.2 单个已发布版本（英文稿）

用途：写入仓库**英文**变更日志（通常是 `CHANGELOG.md`，或仓库既有的英文变更日志文件）中的一个已发布版本节。不要把本模板当成完整 CHANGELOG 文件，也不要把它的文件名写进正文。

使用说明：

1. 打开同目录模板 [`changelog-version-template.md`](./changelog-version-template.md)。
2. 用已核实的事实替换 `{{PLACEHOLDER}}`；散文按英文习惯写，命令、路径、编号、URL 与中文稿保持一致。
3. 需要某个 `OPTIONAL` 块时，去掉包围注释并删除说明文字；不需要或无证据则整块删除，不要留空标题、`None` 或未解开的注释。
4. 将该版本节按第 8.1 节和第 8.4 节，与文件开头、`Unreleased`（若有）以及其他版本一起组装：多个版本按**新到旧**排列。

### 8.3 单个已发布版本（中文稿）

用途：写入仓库**中文**变更日志（通常是 `CHANGELOG-zh-CN.md`，或仓库既有的中文变更日志文件）中的一个已发布版本节。结构必须与英文稿对等，分类集合、条目数量、编号、命令和链接一致。不要把本模板当成完整 CHANGELOG 文件，也不要把它的文件名写进正文。

使用说明：

1. 打开同目录模板 [`changelog-version-zh-CN-template.md`](./changelog-version-zh-CN-template.md)。
2. 基于**同一份事实清单**填写；先同步版本号、日期、分类、条目与引用，再组织中文表述，不要生硬直译。
3. `OPTIONAL` 块的启用与删除规则与英文模板相同；无证据的分类整块删除，不要留空标题。
4. 组装方式与第 8.2 节相同：按新到旧排列，并遵守第 8.1 节与第 8.4 节。

实际落稿时，模板中所有无证据的 `###` 分类都应整块删除，而不是留空标题。多个版本按**新到旧**排列：`Unreleased` 在最前（若有），随后是最新已发布版本。

### 8.4 正文清理要求

- 不要在 CHANGELOG 里保留本规范的说明性段落。
- 不要把“本次由 Agent 生成”之类过程信息写进正文。
- 不要把未发布说成已发布，也不要在正文里催促用户去点 GitHub 的 Publish。

## 9. 交付说明要求

在**正文之外**另附一段简短交付说明。至少包括：

1. **审阅范围与状态：** 仓库、分支或引用、包/模块范围，以及可发布成稿或待核对草稿。
2. **版本 / 时间边界：** 当前版本或 `Unreleased`、上一版本（或写明首次发布）、比较区间、日期依据（含时区），以及已核实的 Compare / Tag URL。
3. **已启用与省略的分类及原因：** 列出实际保留的分类；对明显可能被期待但未启用的分类，用一句话说明原因（无此类变更、无附件、无真实对比区间等）。
4. **未验证命令或 `{{TODO}}`：** 哪些升级/迁移命令已验证，哪些只是摘自仓库但未在本环境执行，以及正文里残留的 `{{TODO}}` 及其原因。
5. **需维护者重点核对的风险点：** 例如可能遗漏的破坏性变更、迁移步骤不完整、子包版本线不一致、旧 CHANGELOG 与 Git 历史冲突、包尚未发布到注册源、校验和未提供、预发布文案是否足够醒目，或发现但未写入正文的疑似密钥。

交付说明要短、具体、可执行，不要重复粘贴一整份 CHANGELOG。

## 10. 最终自检

- [ ] 已做全项目（或用户指定范围）审阅；范围外的变更未写入，范围内对用户有影响的变更未明显遗漏
- [ ] 版本或时间边界可核实；未编造 Tag、上一版本、日期或 Compare 区间；已发布版本写了版本号和日期，`Unreleased` 未冒充已发布
- [ ] 已核对最终交付行为、`Unreleased` 归属、版本节唯一性与标题引用定义（如适用）

- [ ] 日期依据已在交付说明中注明；没有随手填写“今天”
- [ ] 只包含有证据的分类；未启用部分已整块删除（不是“注释着留下来”，也没有 `None` / `无`）；说明性 HTML 注释已从交付正文中去掉
- [ ] 未编造变更内容、性能数据、PR/Issue 编号、贡献者、安装/升级命令、下载链接或校验和
- [ ] 改动写成具体的用户可见变化，而非原始 commit message；无夸大；内部琐碎提交已合并或省略
- [ ] 破坏性变更（若有）紧跟摘要及必要警示，迁移步骤可核实或已标 `{{TODO}}`

- [ ] 无密钥或真实凭证；示例为明显占位符
- [ ] 主升级命令（若有）已展开，或已标明未验证及原因；核心变更条目未被折叠

- [ ] 安全条目（若有）无利用步骤，无编造的 CVE 或严重级别

## 11. 禁止编造与越权发布（再强调）

Agent 交付正文和交付说明，并标明可发布成稿或待核对草稿。可依据第 4 节的公开发布证据记录已发生的发布；已打 Tag、仅有内部记录或计划发布的版本，须先核实公开发布状态。

除非用户在当次任务中明确点名，并指定对象与内容，否则不得：

- 创建、修改、删除或推送 Git 提交、分支、Tag
- 创建、编辑、发布或删除 GitHub Release
- 合并 PR，或在 Issue / PR / Discussion / 聊天 / 邮件中代为发布说明
- 把草稿复制到生产文档站点或其他对外渠道

若用户随后要求入库或发布，先根据交付说明列出待确认的 `{{TODO}}` 与风险点，得到明确授权后再执行；本文本身不构成发布授权。
